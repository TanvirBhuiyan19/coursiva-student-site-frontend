# Internationalisation (multi-language)

The learner site is built multi-language-ready. Today every tenant publishes one language; enabling more is
configuration plus translation files, with no routing or component changes.

## What a language consists of

| Layer             | Where                                 | Owner                     |
| ----------------- | ------------------------------------- | ------------------------- |
| Which languages   | `site.default_locale`, `site.locales` | Tenant dashboard → API    |
| UI copy           | `messages/<lang>.json`                | This repo (translators)   |
| Tenant content    | API responses (`?locale=`)            | Tenant, via the dashboard |
| Formatting        | `Intl` with the request locale        | Automatic                 |
| Writing direction | `<html dir>` from the locale          | Automatic                 |

## URLs (SEO)

Subdirectory model, the Google-recommended default for one domain:

- default language, unprefixed: `learn.acme.com/courses`
- other languages, prefixed: `learn.acme.com/es/courses`, `learn.acme.com/pt-br/courses`
  (language subtag; the full lowercase tag only when two locales share a language)
- `/<default>/…` → 308 to the unprefixed URL; unknown prefixes are ordinary paths (404)

Every indexable page emits `<link rel="alternate" hreflang>` for each language plus `x-default`
(`pageAlternates()` in `features/tenant/server.ts`), the sitemap lists every language with `xhtml:link`
alternates, `<html lang>` and `Content-Language` match the URL, and Open Graph carries `og:locale:alternate`.
Rules live in `src/i18n/locales.ts` (shared by the proxy, server and browser) and are unit-tested.

Request flow: `proxy.ts` splits the prefix → rewrites to `/{tenant}/{locale}/…` → the `[locale]` root param feeds
next-intl (`i18n/request.ts`), `currentScope()` (validated against `site.locales`) and every API read.

## Adding a language — checklist

1. **UI catalogue**: copy `messages/en.json` to `messages/<lang>.json` (e.g. `es.json`, or `pt-BR.json` for a regional
   variant) and translate. Partial files are fine: missing keys fall back `pt-BR → pt → en`. Register the loader in
   `src/i18n/messages.ts`. `src/i18n/i18n.test.ts` validates ICU syntax, keys and placeholders.
2. **API**: return translated tenant content for `?locale=<tag>` (see the contract below) and add the tag to the
   tenant's `locales` in `/site` and the domain-resolution response.
3. **Fonts**: the brand fonts cover Latin + Latin Extended. For Cyrillic, Greek, Vietnamese, Arabic, Hebrew, CJK…,
   add a font with that subset in `app/[tenant]/[locale]/layout.tsx` (or rely on the system fallback in
   `--font-body`/`--font-display`).
4. **Language switcher** (not built yet — no tenant has two languages): a list of `site.locales` linking to
   `localizePath(site, l, currentAppPath)` with a **full page load** (`<a href>`, not client navigation) so cached
   learner data refetches in the new language; label each language in its own language
   (`new Intl.DisplayNames([l], { type: 'language' }).of(l)`) and mark the link `hreflang` + `lang`.
5. **Right-to-left** (Arabic, Hebrew, Persian, Urdu…): nothing to do beyond the rules below — `dir="rtl"` is set
   automatically. Check the pages visually once (`e2e/i18n.spec.ts` covers the basics).
6. Run `npm run check` and `npm run e2e`.

## API contract for translated content

- Server reads send `?locale=<BCP 47>` and `Accept-Language` (`lib/api/server.ts`); the query param keeps each
  language in its own cache entry. Browser calls send `Accept-Language` from `<html lang>`.
- The API returns content in that language, falling back to the tenant default for untranslated fields. Slugs stay the
  same across languages (so URLs map 1:1 and hreflang pairs are exact).
- Revalidation tags are per tenant, not per language — one webhook call refreshes every language of a page.
- Validation/error messages from the API should also honour `Accept-Language` — they are shown to learners verbatim.

## Rules for code (lint- and test-enforced where possible)

- **No UI literals in JSX** — `messages/*.json` + `useTranslations`/`getTranslations` (`i18next/no-literal-string`).
- **Whole sentences as one message** with ICU placeholders/plurals/rich tags — never concatenate fragments, word
  order differs between languages.
- **Links** use `Link`/`useLocalizedRouter`/`useHardNavigate` from `@/i18n/navigation` with locale-less `routes.*`
  paths; compare paths with `useAppPathname()`. Server code builds URLs with `localizePath()` / `pageAlternates()`.
- **Format with the request locale** (`useFormat()`, `lib/format.ts`) — never pass a hard-coded locale, never
  format dates/numbers/money by hand.
- **CSS uses logical properties**: `margin-inline-start`, `padding-inline-end`, `inset-inline-start`,
  `text-align: start`, `border-inline-end` — not left/right. Exceptions: symmetric centring (`left: 50%` +
  `translateX(-50%)`) and media controls (a ▶ never mirrors).
- **Horizontal motion** multiplies by `var(--dir-sign)` (1 in LTR, −1 in RTL); **directional icons** get
  `className="flip-rtl"`; directional glyphs in CSS `content` need a `[dir='rtl']` override. Arrows inside
  translated messages ("View →") are the translator's call.
- **Don't truncate labels to fit English widths** — German and Finnish run ~35% longer; layouts must wrap.
